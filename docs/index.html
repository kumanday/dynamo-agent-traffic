Dynamo replay of Harness Leaderboard agent traffic

A simulation study. Every original trial of a public coding-agent benchmark, 6.6 million model calls, replayed through NVIDIA Dynamo's simulator under four routers. Timing is modelled and no request ran on a GPU, so read the limits before using a number from this page.

Summary

The Harness Leaderboard runs coding-agent harnesses on open-weights models and publishes a per-call log for every trial. This study took every original trial in that public dataset, converted each one into a replayable agent session, and replayed all of them through Dynamo's CPU simulator (aisimulate predict --stack dynamo) under four routers. Every run replays on simulated GLM-5.3-Flash workers with two B300 GPUs each, and at least four workers.

The default KV router missed the latency target on 22 of 216 runs. Session affinity missed it on 1. Setting the KV router's prefill_load_scale to 16 brings it to 8.7B recomputed tokens and the same 215 runs within the target. Timing comes from the simulator's operator-level model, and no request ran on a GPU: read the limits before using a number from this page.

Findings#

  1. The default KV router recomputes 3.1x the tokens that session affinity does. Across the whole dataset it prefills 25.5B tokens against 8.3B, and misses the SLA on 22 of 216 runs against affinity's 1. In 21 runs the default router misses and affinity meets the SLA. No run goes the other way.

  2. The gap concentrates under load. In the median run the default router prefills 1.5x what affinity does, and in the 90th-percentile run 3.2x. When runs that hit one endpoint at the same time are merged, the default KV router meets the SLA in 1 of 13 windows, with 91.2% of requests inside it. Affinity meets it in all 13 and prefills 2.9B tokens against the default router's 13.8B, a 4.8x gap.

  3. One parameter recovers most of it. With prefill_load_scale 16, the KV router comes within 5% of affinity's prefill (8.7B against 8.3B) and meets the SLA on the same 215 runs.

  4. Round-robin prefills 5.9x what affinity does and fails all 13 endpoint windows, with a mean TTFT of 60.9 s.

  5. The ordering holds across traffic sources and harnesses. Hermes meets the SLA on 17 of 25 runs with the default KV router and on all 25 with affinity. DeepSeek Harness goes from 16 to 19 of 19, OpenCode 2.2.6 from 17 to 19 of 19, and Grok Build from 4 to 6 of 6.

  6. Simulated affinity reuses far more than the real endpoints did. Over the same runs, the providers served 91.6% of prompt tokens from cache, and 73.8% of flint traffic. The simulated deployment with affinity reuses 98.6%.

  7. A native DeepSeek-V4.1-Flash replay ranks the routers the same way. One DeepSeek run replayed on simulated DeepSeek-V4.1-Flash: default-router prefill is 3.1x affinity's (508M against 162M tokens), and p99 TTFT is 2.6 s against 571 ms. Its simulated decode speed fails the inter-token SLA under every router.

  8. One run misses the SLA under every router. Flint run 20261109-163846-flint-full-default-0086 (Oh My Pi, 146 peak trials on four workers) reaches a p99 inter-token latency of 111 ms even with affinity. Oh My Pi issues parallel calls, and the pool sizing rule gives it too few workers.

Limits#

  1. The timing is modelled. AISimulate rates agentic replay as functional only. Every latency here comes from its operator-level model on measured B300 kernel data. No request ran on a GPU, so treat TTFT, ITL and SLA counts as simulator output that a hardware run still has to confirm.

  2. Three of the four models are projected onto GLM-5.3-Flash. Every run replays on one target: GLM-5.3-Flash FP8 on vLLM 0.31.0, two B300 GPUs per worker. Traffic recorded on DeepSeek-V4.1-Flash, flint and Ripple-65B-Preview keeps its recorded token counts and takes GLM-5.3-Flash's timing. GLM-5.3-Flash keeps little KV cache per token, so a dense-attention model would run out of KV capacity sooner.

  3. Each run has one pool size. The four routers serve a run on the same number of GPUs, so the comparison shows recomputed tokens and SLA attainment at a fixed size. How many GPUs each router would need is measured only for the two runs in the pool-size section.

  4. Prompt blocks are synthesized. The converter reads no prompt text. Blocks are rebuilt from token counts on the assumption that a context grows by appending. Each call's output counts as new prefill in the next call under every router.

  5. Pacing is closed-loop. Each agent waits for its simulated completions and keeps its recorded tool gaps, so a faster or slower simulated server moves the agent's next call with it. The replay does not reproduce the recorded arrival times.

  6. Endpoint windows are a selected, overlapping set. Of 33 groups of overlapping runs, 13 were replayed: those where merged concurrency rose well above any single run, plus all four flint groups. Their trials also appear in the per-run results, so the two sets of totals cannot be added.

  7. The provider logs show outcomes only. Cached-token counts come from each provider's own reporting. The logs say nothing about the providers' hardware, pool sizes or routing.

Results#

All 216 runs cover 68,905 trials and 6,616,606 requests per router. The 13 endpoint windows cover 26,395 trials and 2,431,809 requests per router. Every replay completed all of its requests.

All runs and endpoint windows#

The KV router's cost adds prefill_load_scale times the uncached prefill blocks to the decode blocks already active on a worker. An active agent request carries about 100k tokens of context, roughly 1,500 blocks of 64 tokens. A worker that holds a request's cached prefix but serves one or two more long sessions therefore scores worse than a worker that has to recompute the whole prompt, and the router gives up the cached prefix. GLM-5.3-Flash's linear and sparse attention also makes long-context decode cheaper than that block count implies.

By harness#

Pool size and GPU count#

Before the full replay, 39 pilot replays varied the pool size from 4 to 32 workers on two runs and on the first 100 trials of each: a Hermes run recorded on flint (526 trials, 84,444 requests, 273 trials at peak) and an OpenClaw run recorded on GLM-5.3-Flash (528 trials, 92,744 requests, 155 trials at peak). Both replay on the GLM-5.3-Flash target. These pilot traces leave out trials on 22 tasks that a separate analysis was holding back at the time, about 11% of each run's trials.

  • Session affinity serves the Hermes run on half the GPUs. On 8 GPUs with affinity, p99 TTFT is 889 ms, prefill is 130.4M tokens and the median trial takes 51.4 minutes. On 16 GPUs, the default KV router gives 5.0 s, 838.1M tokens and 54.9 minutes.
  • More workers make the default KV router worse on the OpenClaw run. Prefill rises from 157.4M tokens on 4 workers to 276.9M on 8. With affinity it stays at 41.5M and 41.6M.
  • Round-robin loses reuse with every doubling of the pool. From 4 to 32 workers on the 100-trial slices, its prefill grows from 18.7M to 125.5M tokens for OpenClaw and from 76.8M to 457.3M for Hermes. Affinity holds at 5.2M and at 19.6M to 21.0M.
  • Raising prefill_load_scale closes most of the gap on the Hermes run. Prefix reuse goes from 90.0% at the default to 96.3% at 4 and 98.0% at 16, against affinity's 98.6%.
  • The reuse bound matters. A trace of the OpenClaw run that treats the provider's own cache misses as prompt changes doubles prefill under the default KV router: 337.7M against 157.4M tokens.

A real endpoint losing its cache under load#

The per-call logs record how many prompt tokens each provider served from its own cache. On DeepInfra's DeepSeek-V4.1-Flash endpoint, all 12 harnesses got 97-99% of prompt tokens from cache, and the provider recomputed at most 0.4% of the prefix an append-only context could reuse. On zai-org's GLM-5.3-Flash endpoint the provider recomputed 0.7-0.9%. The flint and Ripple-65B-Preview endpoints recomputed far more: Kimi Code on flint got 24.0% of prompt tokens from cache against 98.9% reusable, and Hermes on flint got 80.1%.

The flint endpoint shows when that happened. Between 16:00 and 18:00 UTC on 2026-11-09, with up to 195 trials active, it served 97.3-98.8% of prompt tokens from cache. At 22:30 two runs overlapped and active trials reached 395; the cached share fell to 87.7%. It stayed between 45.9% and 78.9% until 03:00, then fell to 14.7% at 04:30 with 73 trials active. The reusable share stayed between 97.2% and 99.5% throughout. The logs cannot show the provider's internals. The pattern is consistent with a pool that grew under load and routes without regard to cached prefixes.

The buckets are in results/pilot/endpoint-timeline.md, and the per-harness table in results/pilot/provider-cache-gap.md. Both come from the pilot extraction of 15,017 trials in 119 runs.

Native DeepSeek-V4.1-Flash cross-check#

Run 20261108-105222-deepseek-v4-1-flash-full-high-f9c1 (1,170 trials, 96,583 requests, 38 trials at peak) also replayed on simulated DeepSeek-V4.1-Flash itself: four workers of four B300 GPUs. The routers rank the same way as on the GLM-5.3-Flash target. Simulated decode averages 57-62 ms per token under every router, above the 50 ms bound, so 1.2-1.4% of requests meet the SLA. That is why the main replay projects DeepSeek traffic onto GLM-5.3-Flash.

Slice check#

Six long runs at low concurrency (63-75 hours of agent time each) took eight hours or more per replay, so they were also replayed as six consecutive slices of trials and recombined. Flint run 20261025-161003-flint-full-default-5596 uses the recombined slices in the results above; the other five use their full replays. On those five, the sliced and full replays agree within 0.1 points of prefix reuse, 3.9% of prefill and 0.1 points of SLA attainment. Sliced p99 TTFT runs up to 25% higher because it takes the worst slice.

Method#

Data#

The Harness Leaderboard is Joel Niklaus's public benchmark of coding-agent harnesses on open-weights models. Trials in its bucket carry a meter log (agent/hlb-meter.jsonl) with one row per model call: start time, time to first byte, latency, and input, cached, output and reasoning tokens. The replay traces are built from those logs and each trial's config.json alone. No prompt text, trajectory content or task result goes into a trace.

The data came from an archived mirror of the bucket, built in two passes: a first snapshot, then every object published after it, found by listing the bucket again and keeping objects whose path and Xet hash were missing from the first snapshot's manifest. The mirror holds runs with IDs dated 2026-10-18 to 2026-11-11. They call four endpoint families: DeepSeek-V4.1-Flash (97 runs), GLM-5.3-Flash served by zai-org (80), flint (23) and Ripple-65B-Preview (16).

Trial identity#

Leaderboard runs reuse trials from earlier runs, so a run directory lists trials that did not execute in that run, and a copied trial's meter log carries the original run's timestamps. Replaying copies would count the same traffic several times. A trial's identity is the Xet hash of its meter log, or of its trajectory when the meter log is missing or under 256 bytes. The first trial that holds an identity, in run ID order, is the original.

Every original has a meter log. The 69,588 originals span 216 runs and hold 6,616,606 successful calls. 683 of them made no successful call, which leaves 68,905 replayable trials.

Trace conversion#

hlb_to_agentic.py converts a run's meter logs to Dynamo's agentic Mooncake v2 trace format (schema: dynamo.agentic_mooncake, version: 2, 64-token blocks).

  • Plays and requests. Each trial is one play and each successful call is one request, with recorded_api_time_ms from the logged latency.
  • Streams. A call continues the idle stream whose last prompt it extends. A call that starts while that stream is busy, or whose prompt is shorter than every stream's (a compaction or a subagent), opens a new stream. Each stream is one session. In the 15,017 trials of the pilot extraction, calls overlap in at most 5% of cases (Oh My Pi) and prompts shrink in about 1%.
  • Dependencies. A stream's next call depends on the completion of its previous call, delayed by the recorded gap, which is tool and harness time. A call also joins another stream that finished after its own predecessor. A new stream spawns from the latest completed call, or from the dispatch of an in-flight call.
  • Pacing. Dependent requests are released on their dependencies alone, so an agent's next call moves with the simulated server's latency.
  • Prompt blocks. Block hashes are built from token counts. A call reuses the whole prompt of its parent when it extends it, which models an append-only context. A trial's first call draws from one prefix chain shared by all trials of the same harness version: the system prompt and tool definitions.

The append-only assumption is an upper bound on reuse, and it is the replay input. On DeepInfra's DeepSeek-V4.1-Flash endpoint the provider's cached share lands within half a point of that bound for every harness, which confirms that these harnesses grow their context by appending. The converter can also build a lower bound, where a call reuses only as many leading blocks as the provider reported cached. That bound encodes the provider's own cache misses as if the prompts had changed.

Replay design#

  • Target. Every run replays on GLM-5.3-Flash FP8 served by vLLM 0.31.0 on B300 SXM, two GPUs per aggregated worker, with default KV capacity (90% memory fraction). GLM-5.3-Flash traffic replays natively. AISimulate has no model for flint or Ripple-65B-Preview, so their traffic is projected onto GLM-5.3-Flash. DeepSeek-V4.1-Flash traffic is projected too. Its measured B300 tables do not cover agent-sized attention shapes; the first miss was one request extending an 8,192-token cached prefix by 178 tokens. In AISimulate's HYBRID mode the missing shapes are priced with speed-of-light estimates, which put decode at 57-92 ms per token against DeepInfra's recorded 5.8 ms median, so every request would miss the inter-token bound. One DeepSeek run replays natively as a cross-check.
  • Pool size. Workers = max(4, ceil(peak concurrent trials / 50)). Four workers are one 8-GPU node, so every run below 200 concurrent trials gets one node and a real routing decision. 884 of the 916 replays used four workers and the rest five to eight.
  • Endpoint windows. make_windows.py groups runs by the endpoint they called and merges runs whose active spans overlapped, which rebuilds the load each endpoint carried.
  • Compute. The 916 replays (9.05M requests per router) took about 9.5 hours on a 176-vCPU machine. Simulation time tracks decode steps more than request count.

SLA definition#

The base configuration sets evaluation.sla to ttft_ms: 2000 and itl_ms: 50. AISimulate counts the requests that meet both bounds (its goodput count). A replay meets the SLA when at least 99% of its requests do. "Runs meeting SLA" counts replays, and "requests meeting SLA" is the share of all requests in a group.

Simulator#

The replays ran on Dynamo commit 3e84909a (ai-dynamo 1.7.0) with the AISimulate release it pins, 0.13.0.dev202610290000000087. Dynamo's Python bindings were built with --features ais-forward-pass, which operator-level timing needs. The configuration sets estimation_mode: op_level and enable_shared_layer: false. The published GLM-5.3-Flash whole-forward profiles are 360-point calibration grids, and agent prefills fall outside them: the first failure was one request prefilling 7,962 new tokens on a short cached prefix. Operator-level timing prices any shape from per-kernel measurements. The base configuration is scripts/sim/glm-b300-op.yaml.

Notes for Dynamo and AISimulate maintainers#

The work turned up four technical points, written up in upstream-notes.md. The issues and pull request filed from them are listed in the repository's Upstream section.

  • Dynamo's replay runner does not advertise engine model controls, so --stack dynamo rejects kvcache_quant_mode and fmha_quant_mode. A small patch forwards them.
  • The KV router's default cost gives up long cached prefixes on agent traffic, with the numbers from this study and three possible directions.
  • Harness Leaderboard meter logs convert to agentic Mooncake v2 traces, with a description of the converter.
  • The aisimulate predict supervisor used about 41% of a core per replay in a 160-replay sweep, SIGTERM left execution processes running, and the 60-second initialization timeout was too short for large traces.
